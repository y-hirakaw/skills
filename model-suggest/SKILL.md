# モデルと effort の選び方

2026年10月時点の Claude 5 系のラインナップが前提。モデルの情報は古くなりやすいので、
ラインナップや料金に自信がないときは公式の [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview) と
[Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model) を確認すること。

## 基本の考え方

1. **迷ったら Opus 5.5 から始める。** 公式も「ほとんどの作業は Opus 5.5 から」としている
2. **モデルを変える前に effort を変える。** 公式は「モデルを変えるより effort の調整のほうが効くことが多い」としている。推奨は必ずモデルと effort の組み合わせで出す
3. **Opus 5.5 を `xhigh` / `max` にしても足りないときだけ Fable 5.1 に上げる**
4. **量が多く速さが要る作業は Haiku 5.5 に下げる**

## ラインナップ（2026年10月）

| モデル | 向いている作業 | effort の初期値 | 料金（入力 / 出力、100万トークンあたり） |
| --- | --- | --- | --- |
| **Fable 5.1** | 最も高い能力が要る作業。数時間続くエージェントの作業、多段の深い調査、完成した文書や資料まで仕上げる分析 | `high` | $10 / $50 |
| **Opus 5.5** | 長時間のエージェント型コーディングと知的作業。大規模なリファクタ、複雑なシステムの設計、画像の多い作業 | `medium` | $4 / $20 |
| **Sonnet 5.5** | 速さと能力の両立。日常のコード生成、データ分析、文章作成、ツールを使う作業 | `high` | $2 / $10 |
| **Haiku 5.5** | 量が多く速さが要る作業。分類、抽出、振り分け、リアルタイム処理、サブエージェントの作業 | `medium` | $0.10 / $0.50 から |

- どのモデルも、コンテキストは 100万トークン、出力は最大 12.8万トークン
- 速さが要るが能力は落としたくないときは、Opus 5.5 の fast mode（出力が最大2.5倍速い代わりに割高）も選択肢になる

## タスクの不確実性で当たりを付ける

タスクを「何がわかっていて、何がわかっていないか」で分類する。ドメイン（コーディング・文章・調査）ではなく、**不確実性のレベル**が判定の軸。

| 分類 | 状況 | 当たり |
| --- | --- | --- |
| **長い探索** | ゴールも道筋も不明瞭で、数時間かけて調べ・試し・仕上げる。Opus 5.5 で足りなかった実績がある | **Fable 5.1** / `high` |
| **探索** | ゴールや方針自体が不明瞭。設計、アイデア出し、原因不明の不具合、リファクタの方針 | **Opus 5.5** / `high`〜`xhigh` |
| **調査要** | ゴールは明確だが、コードベースや既存の実装を理解してから動く必要がある | **Opus 5.5** / `medium`、または **Sonnet 5.5** / `high` |
| **定型** | ゴールも手順も明確。README の確認、規約違反のチェック、翻訳、整形、分類、抽出 | **Haiku 5.5** / `medium` |

### 分類のシグナル例

**長い探索（Fable 5.1）**
- 「一晩かけて調べて」「資料まで仕上げて」「何時間かかってもいい」
- 同じタスクを Opus 5.5 の高い effort でやって、質が足りなかった

**探索（Opus 5.5 / effort 高め）**
- 「どうすべきか」「方針を決めたい」「設計してほしい」「アーキテクチャ相談」
- 「うまくいかないが原因不明」「なぜこうなるか分からない」
- 前提が曖昧なまま始まっている、ゴールが変わりうる

**調査要（Opus 5.5 / medium、または Sonnet 5.5）**
- 「実装して」「修正して」＋ファイル名や既存機能への言及
- 「この PR のレビュー」「このコードを改善」
- ゴールは見えているが、現状の把握が先に必要
- 速さを優先したい、または料金を半分にしたいなら Sonnet 5.5

**定型（Haiku 5.5）**
- 「〇〇って README に書いてある？」「このコード規約に違反してない？」
- 「この関数の型を教えて」「翻訳して」「フォーマットして」
- 同じ処理を大量に回す（分類、抽出、振り分け）

## 組み合わせる

1つのモデルで全部やるより、組み合わせたほうが安く済むことが多い。

- **強いモデルが全体を回し、量の多い作業を安いモデルに任せる**：Claude Code なら、本体は Opus 5.5、ファイルの探索や大量の要約をするサブエージェントは Haiku 5.5 または Sonnet 5.5
- **安いモデルが作業し、難しい判断だけ強いモデルに聞く**：定型の処理を Haiku 5.5 で回し、判断に迷うものだけ Opus 5.5 に回す

## 出力フォーマット

必ずこの形式で回答する：

```
推奨: [モデル] / effort [low / medium / high / xhigh / max]
理由: [タスクのどこが判定の根拠か、1〜2文で]
足りないとき: [effort を上げる → それでも足りなければ次のモデル、の順で]
組み合わせ: [サブエージェントなどを分けると効く場合だけ。なければ省略]
```

## 格上げバイアス

分類に迷ったときは**強い側に倒す**こと。

- 弱い側から強い側に上げるコスト：少し高くなるだけ（Opus 5.5 と Sonnet 5.5 の料金の差は2倍）
- 強い側から弱い側に下げるコスト：気づかないまま間違った答えが返る

ただし、上げる順番は「effort を上げる」が先で、「モデルを上げる」はその後。
信頼度が低いと判断したときは、「足りないとき」欄で「迷うなら Opus 5.5 の effort を上げる」と明示する。

## API で使う場合の注意

Claude Code ではなく API でモデルを切り替える相談のときは、次の破壊的な変更に触れる。詳しくは各モデルの移行ガイドを確認する。

- Opus 5.5 と Fable 5.1 は思考（adaptive thinking）が常に有効で、止められない
- Opus 5.5 と Sonnet 5.5 は、ツールの強制指定（`tool_choice` の `any` / `tool`）に対応していない
- 古いモデルの extended thinking（`budget_tokens`）は、新しいモデルでは受け付けられない

## 背景（判定の文脈として）

不確実性の分類は Cynefin フレームワークの Clear / Complicated / Complex にほぼ対応している。
「タスクの不確実性に応じて道具を変える」という設計思想。

手動運用が前提：ユーザーが「迷ったら聞く」タイミングでだけ発動させるのが最もロバスト。
将来的にはconfidenceスコア付きルーターへの進化も視野にあるが、まずはこのスキルで判定ログを溜める。
