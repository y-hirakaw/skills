# 簡易セキュリティチェック

セキュリティの専門家ではない開発者が、設計を見たときに決まった問いを立てられるようにするためのチェック。
細かい攻撃手法を網羅するものではない。**入られた前提で、どこまで届いてしまうかを小さくする**ことと、**守りの費用が被害に見合っているか**を見る。

## 手順

1. 対象（設計書、API 定義、PR の差分、画面の説明）を読み、次を書き出す
   - 扱うデータ（特に個人情報、認証情報、カード情報、本人確認書類）
   - 入口（API、画面、管理画面、運用ツール、バッチ、社内の呼び出し、トークンや API キー）
2. 下の7つの問いを順に当てる。答えが設計から読み取れないものは「書かれていない」として指摘する
3. 出力フォーマットで返す

## 7つの問い

1〜6 は「セキュアじゃない」を見つけるため、7 は「過剰」を見つけるため。

1. **何を持つのか**
   - その情報は本当に要るか。いつ消すか
   - 「あとで使うかも」「分析に使えるかも」は理由にならない。分析なら特定できない形（年代、都道府県、別の ID）で足りることが多い
   - 自分で持たずに済まないか（カード → 決済代行会社、ログイン → IdP、本人確認 → 専門サービスで結果だけ持つ）
   - 退会者や、手続きを完了しなかった人の情報を持ち続けていないか。残す理由があるなら、期限を決め、ふだんのシステムから切り離した場所に置く
2. **誰がどこまで届くのか**
   - この API・画面・トークンで、誰の、どの項目に、どれだけ届くか
   - 1つの入口から全員分に届かないか（数百万件の流出はほぼこれ）
   - URL の ID を書き換えると他人のデータが見えないか（OWASP API Security Top 10 の1位、BOLA）。自分のデータなら `/me` にして ID を URL に出さない
   - 返す相手ごとに返す項目が絞られているか。丸ごと返して画面で絞っていないか
   - 見る権限と、まとめて書き出す権限が分かれているか。大量の取得に上限や通知があるか
3. **権限を決めていないときはどうなるか**
   - 権限の判定が1か所にまとまっているか。API ごとに if 文で書いていないか
   - ルールが書かれていない API は、拒否になるか（書き忘れが穴にならないか）
   - 権限がないときに、データの有無が伝わらないか（403 より 404）
4. **例外の道はあるか**
   - 管理者なら通す分岐、サポートのなりすまし、社内の呼び出しを信用して飛ばすチェック、全件を扱うバッチ用のキー、古いバージョンの API
   - 例外に範囲・期限・承認があるか。使ったら記録と通知が残り、誰かが気づけるか
   - 管理者・運用の入口が、ユーザー向けと分かれているか
5. **同じところに置いていないか**
   - 暗号化の鍵とデータ（鍵は KMS に置き、アプリは鍵を持たない。環境変数や CI の Secrets に置いていないか）
   - 個人情報とほかのデータ、本番とバックアップ（別アカウント）、本番と開発
6. **盗まれたらどうなるか**
   - セッションやトークンが盗まれたら、何ができて、どれくらいの間使えて、どうやって止めるか
   - Cookie は `HttpOnly`・`Secure`、トークンを localStorage や URL やログに置いていないか
   - 有効期限、更新用トークンの使い回しの検知、全端末のログアウト、新しいログインの通知
   - 個人情報の全表示や大事な変更の前に再認証を求めるか
   - フィッシングに強い認証（パスキー）を使えるか
7. **漏れたらいくらかかるか（過剰の判定）**
   - 件数と中身から見た被害（個人情報保護委員会への報告、本人への通知、問い合わせ窓口、お詫び、信用）
   - それに対して、提案している守りの費用（構成の追加、運用、作る手間、使い勝手の低下）は見合っているか
   - 先にお金のかからない守り（持たない・消す、デフォルト拒否、`/me`、返す項目を絞る、大量取得の制限、記録）で足りないか。分離や項目ごとの暗号化のような費用のかかる守りは、本当に持たなければいけない機密性の高いものに絞る

## 出力フォーマット

```
## 対象の整理
- 扱うデータ: …
- 入口: …

## 指摘
| 重さ | 問い | 指摘 | 提案 |
| --- | --- | --- | --- |
| 高 | 2 | … | … |

## 過剰かもしれないもの
- …（なければ「なし」）

## 設計から読み取れなかったこと
- …
```

- 重さは「高（全員分に届く、認証・認可を飛ばせる）」「中（1人分に届く、盗まれたときに長く使える）」「低（備えとしてあるとよい）」
- 指摘は、どの問いに引っかかったかの番号を付ける。推測で断定しない。設計に書かれていないことは「書かれていない」と書く
- 「過剰かもしれないもの」は、問い7に照らして費用が被害に見合わない守りを挙げる。セキュリティを弱める提案になる場合は、何を受け入れることになるかを一緒に書く

## 注意

- これは簡易チェック。決済、医療、金融など規制のある領域や、大規模な個人情報を扱う設計は、専門家のレビューも勧める
- 指摘を増やすことが目的ではない。人が「本当に危ないか」「過剰か」を判断できる材料を出す
